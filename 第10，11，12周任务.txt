第十周任务  存储过程与函数
1. 本周目标
在 v1.0 数据库的基础上，将补货选择、订单完成、库存调整和折扣等业务写成可重复调用的存储过程和函数。所有对象都要带参数，完成输入检查和错误处理，并用正常和异常数据进行验证。
2. 任务
1. 编写销售统计存储过程：输入开始日期和结束日期，统计订单数量、销售数量、销售金额以及商品销售情况。检查日期范围，正确处理没有销售记录的情况。
2. 编写库存调整存储过程：输入商品编号、调整数量、调整原因和操作员工编号。商品不存在、调整数量为零或库存不足时，应拒绝操作；调整成功后保存新的库存数量和调整记录。
3. 编写补货量函数：根据当前库存、最低库存量或目标库存量计算补货数量。库存已经达到目标时返回 0，商品不存在时进行明确处理，返回值不能为负数。
4. 编写销售汇总表值函数：输入日期范围，返回商品编号、商品名称、销售数量、销售金额和订单数量等汇总结果，并能够在 SELECT 语句中调用。
5. 完成折扣计算业务：根据会员身份、订单金额或商品分类计算折扣率和折扣金额。折扣计算应使用函数，历史订单中的实际折扣和成交价应保存到订单或订单明细中。
6. 整合任务：将以上过程与函数整合进之前完成的v1.0 数据库，以上业务在数据库中实现，如果之前的应用程序中已经实现，将原先的实现替换。在 SQL Server 中完成，只在页面层中调用
3. 本周作业
procedure.sql：存储过程代码。
function.sql：函数代码。
调用与测试脚本：测试补货、订单完成、库存调整和折扣业务的正常输入、空值、错误编号、错误日期、非法数量、非法折扣和重复调用。
区分存储过程与函数
结果记录：保存输入参数、预期结果、实际结果、成功结果、错误提示以及未写入不完整数据的验证结果。
4. 提示与常见问题
存储过程适合完成选择补货、订单完成和库存调整等会改变数据的业务；函数适合完成补货量、折扣和销售汇总等计算或查询。
日期统计要说明开始日期和结束日期是否包含当天；不要把商品编号和日期直接写死在过程或函数中。
过程和函数的参数、表名和字段名应与数据库设计保持一致；测试时同时准备正确数据和错误数据，并保存错误处理结果。

第十一周任务  触发器与窗口函数
1. 本周目标
使用触发器自动记录库存变化并检查订单完成条件，使用窗口函数完成排名、累计值和移动平均查询。重点理解触发器的自动执行方式，以及窗口函数在保留明细行的同时完成统计的方法。
2. 任务
1. 编写库存审计触发器：库存增加、减少或修改时，自动记录商品编号、调整前数量、调整后数量、变化数量、操作时间、操作类型和操作人员。
2. 编写订单完成规则触发器：订单状态改为已完成时，检查订单明细、商品、购买数量、库存和订单金额。条件不满足时拒绝修改，已经完成的订单不能重复完成。
3. 完成排名查询：使用 RANK、DENSE_RANK 或 ROW_NUMBER，按照销售数量、销售金额或订单数量对商品进行排名，并说明排名结果的业务含义。
4. 完成累计值查询：按照订单日期或商品顺序，统计累计销售金额或累计销售数量，并明确查询的排序字段。
5. 完成移动平均查询：计算最近 3 天、最近 3 笔订单或最近 3 个月的平均销售量或销售金额，并说明窗口范围和业务用途。
3. 本周作业
trigger.sql：提交库存审计触发器和订单完成规则触发器。
window_query.sql：提交一条排名查询、一条累计值查询和一条移动平均查询。
测试脚本：测试单条插入、单条修改、多条修改、正常操作、非法数据和触发器拒绝操作。
结果记录：保存审计记录、订单状态、排名、累计值和移动平均的查询结果，并说明结果是否符合业务预期。
4. 提示与常见问题
SQL Server 触发器一次可能处理多行数据，不能只用一个变量保存一行数据，应结合 inserted 和 deleted 进行判断。
触发器应同时考虑插入、修改和删除，且不宜加入过多复杂业务，以免影响普通增删改操作。
窗口函数不会减少原始数据行数，而是在每一行旁边增加统计结果。累计值要设置明确的排序方式，移动平均要说明窗口大小。

第十二周任务  递归查询与业务事务
1. 本周目标
完成一项层级递归查询；实现订单完成事务和模拟补货入库事务，并验证提交与回滚。两项业务均应明确涉及的数据、修改顺序和失败后的恢复结果，为下一周并发实验准备可重复运行的脚本。
2. 任务
1.梳理事务入口与测试数据：沿用现有数据库，列明订单、订单明细、库存、补货记录和审计表的关系。准备商品P、Q及库存、含多种商品的订单、待入库补货单，并保存初始值。统一库存扣减入口：若原Web程序已在下单时扣库存，本周应将这段业务整合到订单完成事务中，或明确下单即完成；已经完成并扣过库存的订单不能再次扣减。
2.完成层级递归查询：以“商品分类—子分类”为例，建立带父级编号的层级关系，准备根节点、子节点、孙节点和另一条分支。使用递归CTE，从指定分类查出其全部后代，输出编号、父级、层级和路径。分别查询根节点、中间节点、叶子节点及不存在的编号，对照样例关系检查结果。
3.实现订单完成事务：以一个待完成订单为输入，检查订单状态、明细、数量和库存；按商品汇总需求量，扣减对应库存，核算或核对订单金额并更新完成状态，最后统一提交。不存在、已完成、无明细或库存不足的订单应返回明确结果。若下单即完成，订单和明细的创建也应纳入同一事务。说明事务边界及与原存储过程、触发器的调用关系，保证一次业务只扣减一次库存。
4.实现模拟补货入库事务：使用人工填写的补货单和数量，检查商品、数量及单据状态；在同一事务内增加库存，写入或更新补货明细、入库时间和状态，全部成功后提交。再次执行同一已入库单据不能重复加库存。保留补货单编号、商品和数量的对应关系，第四阶段将用预测结果替换人工输入。
5.逐项验证提交、回滚与重复调用：验证业务的正确性，重复调用不再增加。失败用例在库存增加后、单据完成前触发错误，验证库存和补货记录恢复。另检查库存不足、补货量非正数的拒绝结果。每次测试前重置数据。
6.整合任务：将以上过程与函数整合进之前完成的v1.0 数据库，以上业务在数据库中实现，如果之前的应用程序中已经实现，将原先的实现替换。
3. 本周作业
recursive_query.sql：层级表或已有结构说明、样例数据、递归查询及根节点／中间节点／叶子节点／不存在编号的结果。
order_transaction.sql、restock_transaction.sql：两项事务实现、输入参数、测试数据准备及调用顺序。脚本可调用已有过程，不必重复实现相同规则。
验证记录：按“初始数据—操作—预期结果—实际结果”保存订单与补货各自的正常提交、中途失败回滚、重复调用，以及业务规则拒绝结果。检查涉及的全部业务表，不能只展示报错。
更新README和阶段报告材料：说明递归逻辑、事务边界、对象调用关系及分工。保留ai_log，记录AI辅助、人工修改与验证结论；未使用则注明。
4. 提示与常见问题
递归CTE需要起点、递归连接和终止条件；父级外键不能阻止层级成环。测试时设置合理的MAXRECURSION上限，路径列在起始部分和递归部分保持一致的数据类型及长度。
事务失败用例要发生在已经写入部分数据之后；只在执行前拒绝非法参数，不能证明回滚有效。可在测试分支使用THROW主动触发错误。
库存扣减应使用带库存条件的更新并及时检查受影响行数，例如仅在库存≥需求量时扣减；不能只在事务外先查一次库存就认定后续一定充足。
由明确的一层负责整个事务，避免Web程序、存储过程和触发器重复扣减或各自提交。触发器对同一事务内业务表的修改通常也随事务回滚；不要把这类审计表当作独立的失败日志。
实验在项目数据库副本或可恢复数据上进行；结束后检查@@TRANCOUNT，清理未结束事务。第12周完成的是第三阶段的一部分，下一周还需提交并发实验与阶段汇总。

# 阶段报告 · v1.0（第 5—9 周）

> 校园咖啡店线上点单自取系统 · 数据库系统原理实验
> 本阶段目标：在 v0.1 数据库基础上完成 ER 复核、函数依赖与规范化、v0.1→v1.0 迁移与回归，以及分层 Web 应用与测试。
> v0.1 阶段报告见 [v0.1_第1-4周.md](v0.1_第1-4周.md)。

## 一、设计说明（第 5—6 周）

> 分析对象与 ER 图：20 张表与 ER 实体一一对应；ER 图见 [`week5.ER/ER图.png`](../week5.ER/ER图.png)，实体、联系与基数见 [`week5.ER/ER图.md`](../week5.ER/ER图.md)。

### 1. 设计思路

第六周的目标不是「为了拆表而拆表」，而是**用函数依赖检验 v0.1 的关系模式是否合理**，只修正真正违反范式或码定义的地方。分析按 1NF → 2NF → 3NF 逐层推进：先确认字段原子（1NF），再检查复合候选码是否存在部分依赖（2NF），最后排查非码属性间的传递依赖（3NF）。

项目在 v0.1 就确立了三条规则，使大多数表天然落在高范式：

- **关系实体分离**：多对一/一对一只存外码，多对多用关联表，不在双方互塞主码；
- **候选键元素唯一**：用单列自增代理码做主码，复合码只出现在关联表，且每个分量都是外码；
- **逻辑关系分离**：非码属性之间不存在与主码无关的决定关系，杜绝 `A → B → C` 的传递依赖。

### 2. 函数依赖与分解依据

关键函数依赖与对应的设计决策：

- `product_id → category_id`，且 `category_id → category_name` 落在 `categories` 表。若把 `category_name` 冗余进 `products`，就会出现 `product_id → category_id → category_name` 的传递依赖（3NF 违例），并引发插入/修改/删除异常（见 `week6.关系属性码分析.md` §4.3 反例演示）。当前结构把分类名单点存储，三类异常同时消除。
- `product_id → product_name`（商品编号决定当前名称），但**商品编号不决定历史订单成交价**——`order_items` 存下单时的 `product_name`/`sku_name`/`unit_price` 快照，改价不污染历史订单，避免经典修改异常。
- `employees.user_id` 是候选码，候选码不得取 NULL；v0.1 让它可空是码选取错误，故收紧为非空。
- `product_name → product_id`（商品名全库唯一），补唯一约束坐实候选码。

**结论：20 张表满足 1NF/2NF/3NF，并达 BCNF/4NF，无需拆表；仅两处属性级修正（列非空 + 唯一约束）。** 因无表拆分，无损连接（所有表原样保留、外码不变）与依赖保持（依赖集合不变、唯一约束反而加强依赖）天然成立。

## 二、迁移与回归

### 1. 实验过程（迁移步骤）

1. 用 git 对比 v0.1（`e4e7716`）与目标结构，锁定唯一的实质变更：`employees.user_id` 可空→非空，以及其连带的数据迁移（无账号员工「王强」）。
2. 从 git 重建 v0.1 副本到 `week6.v0.1基线/`，记录迁移前基准（订单明细 5 行、商品销量 拿铁4/66·美式1/12、低库存 1 行）。
3. 编写 `09_migration.sql`：基线检查 → 重复检查（商品名/员工账号无重复）→ 回填王强账号 `wangqiang`(5)+店员角色 → `ALTER` 收紧非空 → 加 `product_name` 唯一约束 → 迁移后核对；整体 `XACT_ABORT ON`，任一步失败回滚。
4. 编写 `10_regression.sql`：关键标识、关系映射、订单金额自洽、销量、库存、角色权限，及合法写成功 / 非法外码 / 非法数量 / 越权失败。

### 2. 回归结论与实验总结

- **迁移前后业务含义一致**：订单明细 5 行、商品销量（拿铁 4/66、美式 1/12）、低库存 1 行，迁移前后完全相同，证明迁移只动了账号/员工归属，未改交易、商品、库存。
- **行数变化合理**：无拆表导致的合理行数变化；唯一变化来自数据迁移——`users` 4→5、`user_roles` 4→5（回填账号），其余表不变。
- **两处冗余均有维护手段**：`order_items` 快照用于隔离历史订单、`orders.total_amount` 聚合用于免实时求和，二者分别由「下单一次性快照」和「自洽核对（订单总额=明细合计，0 行差异）」兜底。
- **完整性/权限正反例**：合法写入成功、非法外码与非法数量被拒（消息 547）、越权读取与越权 DDL 失败（消息 229），说明约束与授权在迁移后仍生效。

| 项目 | 迁移前（v0.1） | 迁移后（v1.0） | 差异 |
| --- | --- | --- | --- |
| 订单明细 | 5 行 | 5 行 | 无 |
| 商品销量 | 拿铁咖啡 4 件 / 66.00，美式咖啡 1 件 / 12.00 | 同左 | 无 |
| 低库存（<10） | 1 行（8） | 1 行（8） | 无 |
| `users` | 4 | 5 | +1：回填 wangqiang |
| `user_roles` | 4 | 5 | +1：店员角色 |
| 其余表 | — | — | 行数不变 |

实际运行输出结果正常：迁移前后三项基准一致；行数变化仅 users、user_roles 各 +1，其余不变；无需额外截图。

## 三、应用程序的完整流程

### 1. 目标与选型

第 7—9 周把 v1.0 数据库用到程序里：登录、商品/库存/订单/明细操作、角色权限、事务边界、统一异常与测试。技术选 Flask 3.1 + Jinja + 原生 fetch + pyodbc：本机已有 Python 3.13 与对应依赖，ODBC Driver 18 可直接连 SQL Server，不额外引入 Java 构建链。

### 2. 分层与调用

| 层 | 目录 | 职责 |
| --- | --- | --- |
| 页面层 | `app/web/`、`app/templates/`、`app/static/` | 渲染页面、接收请求、调用业务层、统一返回结构 |
| 业务层 | `app/services/` | 参数校验、业务规则、角色范围、事务边界 |
| 数据访问层 | `app/dal/` | 唯一碰 SQL Server 的层：参数化 SQL、连接与结果读取 |
| 公共设施 | `app/config.py`、`db.py`、`errors.py`、`auth.py` | 配置、连接/事务、统一异常与日志、登录态 |

调用链是页面 → 业务 → 数据访问 → 数据库；页面层不出现 SQL 字符串。应用使用受限账号 `login_app`（`db_app` 角色），只授应用需要的表与操作，无 DDL、无越界表权限；行级过滤（只能看自己的订单）由业务层完成。

### 3. 角色与权限

| 角色 | 可执行范围 |
| --- | --- |
| 顾客 | 浏览商品/规格；下单；看自己的订单；待支付订单明细增删改；支付（模拟）；取消未支付订单 |
| 店员 | 看全部订单与明细；推进 已支付→制作中→待取餐→已完成；查询与调整库存 |
| 店长 | 商品与规格维护；库存调整；订单只读 |
| 系统管理员 | 按店长视图处理，不开放系统管理界面 |

页面按角色隐藏按钮，后端再次校验；数据库层用 `db_app` 权限兜底，形成「界面提示 + 后端规则 + 数据库授权」三道限制。

### 4. 关键实现

- **参数化**：数据访问层全部使用 `?` 占位符，用户输入不拼接进 SQL；关键字查询、登录、订单参数均如此。登录密码用 PBKDF2 哈希校验，会话只存用户与角色。
- **事务与防超卖**：下单、加明细、改数量、删明细、取消都在一个事务里；扣库存用 `UPDATE ... WHERE quantity >= ?` 的条件更新，影响行数为 0 即库存不足并回滚整单；明细数量按差额扣/补，取消与删除明细回补库存。
- **订单号与状态**：订单号由时间戳 + 随机串生成；状态只在允许的转移表内推进，非法转移返回业务错误；支付是模拟动作，只改订单状态与支付时间。
- **统一异常与日志**：响应统一为 `{code, message, data/request_id}`；4001 参数、4010 未登录、4030 无权限、4040 不存在、4090 业务规则、4099 约束冲突、5000/5001 系统与连接错误。前端只显示友好提示，SQL、堆栈、连接信息只写 `logs/app.log`，日志带请求标识、时间、操作、角色、错误码与结果。

### 5. 典型流程

1. 顾客 alice 登录 → 商品/下单（[截图](../week7-9/截图/顾客下单.jpg)）→ 我的订单 → 支付（模拟）或取消；
2. 店员 bob 登录 → 订单详情推进到下一状态（[截图](../week7-9/截图/店员推进订单.jpg)）→ 库存查询/调整；
3. 店长 carol 登录 → 商品与规格维护、库存调整（[截图](../week7-9/截图/店长调整库存.jpg)）→ 订单只读。

权限差异由页面按钮隐藏、后端角色校验与 `db_app` 受限账号三层保证。

### 6. 功能范围

登录；商品列表/详情/新增/修改/删除；规格新增/修改；库存查询/调整；下单；订单列表与详情；明细增删改；支付；取消；状态推进。系统管理员、优惠券、评价、积分与支付网关不在本期应用范围。

## 四、测试与验收

- **测试脚本**：`tests/` 下 pytest + Flask test client，直接打真实库。覆盖登录成功/失败、未登录、越权、参数错误；商品新增/编辑/删除与「删除被引用商品」的约束冲突；库存查询/调整与非法数量；下单扣库存、明细加改删、支付、取消回补、非法状态转移、库存不足回滚；顾客只能看自己的订单；数据库连接失败（模拟）；注入串按普通文本处理。
- **运行方式**：先重跑 `02_insert_sample_data.sql` 回基线，再执行 `python -m pytest tests -q`；测试会写数据，跑完可再重跑 02 复位。测试运行正常。
- **安全测试**：参数化查询（注入串当普通文本）、未登录 401、越权 403、参数错误 400、约束冲突 4099、数据库连接失败 5001；前端只显示友好提示，SQL、堆栈与连接信息只进日志。
- **验收**：按顾客、店员、店长三个角色走通主流程；越权/未登录/参数错误能看到统一提示；SQL 与堆栈不出现在前端。截图见 `week7-9/截图/`（流程示意）。

## 五、实验总结（v1.0）

1. **数据边界与关系设计**：按持久化需求、安全合规、事务一致性、性能划分进库范围；20 张表用代理码做主码、业务自然码做候选码、外码承担引用完整性，`order_items` 为历史凭证保留快照冗余。
2. **规范化与迁移**：逐表检查 1NF/2NF/3NF（并确认 BCNF/4NF），结论是无需拆表，只修正 `employees.user_id` 可空与 `products.product_name` 未落唯一约束两处；在 v0.1 副本上迁移并回归，订单明细、销量、库存迁移前后一致，行数变化仅来自给无账号员工补账号。
3. **应用分层**：页面、业务、数据访问、数据库四层职责清楚；参数化、受限数据库账号、后端角色校验和统一异常把安全边界落到了代码与数据库两侧。
4. **事务与一致性**：下单与明细调整以事务包住订单、明细、库存三处写入，条件更新防超卖；取消与删除明细回补库存；订单总额由明细汇总并在变更后同步。
5. **可复现**：空库按 `01`→`02`→`06`→`07`→`08` 建出 v1.0 并启动应用；第六周迁移按 `week6.v0.1基线` → `09` → `08` → `10` 复现；启动、测试与验证要点见 `README.md`。
6. **边界**：支付为模拟；优惠券/评价/积分/系统管理不在应用范围；商品名全库唯一、有引用时不可删除；规格删除未开放；行级权限由应用承担，数据库只到表/列级。
